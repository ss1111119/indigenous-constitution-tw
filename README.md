用公開資料理解臺灣原住民族的人口、土地、選舉與政治代表性，並提供憲政制度的席次模擬。

## 本機預覽

網站沒有 build step、沒有 npm 相依，但**有一個組建步驟**：發佈目錄由腳本組出。

```sh
python scripts/build-site.py          # 組出 _site/
python -m http.server 8765 -d _site   # 開 http://127.0.0.1:8765/
```

改完前端要重跑第一行。**不要直接用靜態伺服器開 `site/` 目錄**——那樣載不到資料。

這是刻意的：若 `site/` 直開與 `_site/` 都能運作，就存在兩套資料路徑解析邏輯，
而兩者的分歧只會在部署之後才被發現。本機預覽走與 CI 相同的單一路徑，
「本機能跑」才是「線上能跑」的有效證據。詳見
[`openspec/specs/site-deployment/spec.md`](openspec/specs/site-deployment/spec.md)。

資料路徑在程式碼中只有一個定義處：`site/js/state.js` 的 `DATA_BASE`。
新增面板資料時，除了在前端載入，也必須加進 `scripts/build-site.py` 的
`REQUIRED_DATA` 清單，否則本機測得到、線上缺檔。

## 部署

推送到 `master` 時由 GitHub Actions 自動組建並發佈到 GitHub Pages。

首次設定需要在 GitHub repo 的 **Settings → Pages → Build and deployment → Source**
選擇 **GitHub Actions**（不是 "Deploy from a branch"）。這一步在 repo 設定裡，
無法由版本庫中的檔案保證，是唯一必須手動確認的環節。

`_site/` 是組建產物，不入庫。

## 資料更新

人口資料（戶政司 ODRP013／ODRP018）由排程流程自動更新，不需要有人記得跑腳本。
選舉資料與保留地資料**不在自動更新範圍**——前者每次選舉才變動且欄位順序會無預警改變，
後者為年度更新且需人工點擊下載，都需要人工判讀版面。

### 排程與探測

`.github/workflows/refresh-data.yml` 每日 UTC 21:00（臺北時間隔日 05:00）執行。
ODRP 的發布日不固定、滯後約兩個月，所以是每日探測而非按月推算。

探測自 `data/sources.json` 記載的期別次月起逐月查到當月，取最新一個
**ODRP013 與 ODRP018 都有資料**的期別。判定依據是回應的 `responseMessage` 與資料列數，
不是 HTTP 狀態碼——ODRP 對尚未發布的期別回傳 200 並在訊息中標示查無資料。

沒有新期別時流程正常結束、不提交、不部署。網路錯誤或無法歸類的回應則讓流程失敗，
不會被當成「沒有新資料」靜靜略過。

本機可單獨執行探測：

```sh
pwsh scripts/probe-odrp-period.ps1                      # 依 sources.json 的記載期別探測
pwsh scripts/probe-odrp-period.ps1 -RecordedPeriod 11505  # 指定起點，用於驗證探測邏輯
```

### 手動指定期別

在 GitHub 的 **Actions → Refresh population data → Run workflow** 填入 `period`（如 `11507`）即可
略過探測直接轉該期。**指定期別只跳過探測，不跳過任何驗證**——被幅度檢查擋下的期別，
單純重跑同一期會以完全相同的方式再失敗一次。要放行那種期別另見下一節。

重跑版本庫現有期別是安全的：產出與既有檔案逐位元組相同，因此不會產生 commit，
也不會觸發部署。

### 幅度檢查被擋下時

轉檔會在全國原住民總人口相對前一期變動超過 **±1%** 時中止、不產出檔案、流程紅燈，
並在 stderr 印出前後兩期的數值與變動百分比。這道檢查抓的是「內部一致但整份資料換了口徑」，
那種資料能通過所有加總驗證。

處置步驟：

1. 讀流程紀錄裡的前後兩期數值，判斷是資料異常還是真實的大幅變動。
2. 若是**來源異常**（口徑改變、欄位語意變動）：不要放行。先確認上游發生什麼事，
   必要時調整轉檔腳本，再重跑。
3. 若確認是**真實變動**：以下一節的具名放行重新觸發該期。人工確認的責任在此，
   流程不會自己放寬門檻。
4. 兩種情況都不要為了讓流程變綠而調高門檻——**門檻沒有調整的入口**，這是刻意的：
   門檻調高一次，下一次數量級錯誤就過得去了。

### 具名放行一次真實的大幅變動

被幅度檢查擋下的期別，唯一的放行方式是**具名的人工覆寫**：明確表示接受，並寫下理由。
沒有「關掉檢查」或「調高門檻」的選項。

**只能由 `workflow_dispatch`（手動觸發）使用。** 排程執行一律不帶放行參數——排程長期
無人看管，若它能自我放行，這道檢查就擋不住任何東西。

在 **Actions → Refresh population data → Run workflow** 填入：

| 輸入 | 值 |
| --- | --- |
| `period` | 要轉的期別，如 `11508` |
| `accept_large_change` | 勾選 |
| `override_reason` | 具名的人工理由，例如「西拉雅族首批身分登記，已與原民會 11508 月報逐縣市核對」 |

`accept_large_change` 與 `override_reason` **必須同時提供**。只勾選而不填理由、
或只填理由而不勾選，流程都會在下載與轉檔之前就失敗並指出缺少哪一個。
理由要寫成「為什麼確認這個變動是真實的」，不是「讓流程過關」——它會被寫進 commit 訊息，
是三個月後唯一能判斷當時那次跳動是真實變動還是沒人看的意外的依據。

放行時 commit 訊息會追加一段，記錄**實際變動百分比**與**放行理由**原文，例如：

```
⚠️ 本期的變動幅度檢查由人工具名放行：變動 7.8123%，超過 ±1% 門檻。
放行理由：西拉雅族首批身分登記，已與原民會 11508 月報逐縣市核對
```

**放行只鬆綁幅度檢查這一道門檻。** 族別加總等於原住民合計、平埔兩組平行結構不得混加、
原住民族地區代碼齊全等自我驗證一律照常執行，任一不過仍然中止、不產出檔案、流程紅燈。
換句話說，放行能讓「真實但很大的變動」通過，不能讓「內部矛盾的資料」通過。

本機等價指令（兩個參數同樣必須並用）：

```sh
pwsh scripts/build-population.ps1 -Period 11508 \
  -AcceptLargeChange -OverrideReason "西拉雅族首批身分登記，已與原民會 11508 月報逐縣市核對"
```

> **尚未在真實的 GitHub Actions 執行中驗證過。** 腳本端的放行行為有回歸測試涵蓋
> （見「回歸測試」一節），workflow 端的參數解析與 commit 訊息組裝目前只做過本機模擬。
> 首次實際使用時請確認產生的 commit 訊息確實含有理由與百分比。

### 資料更新後的來源記錄

每個新期別在 `data/sources.json` **新增**一筆記錄，既有期別的記錄不被覆蓋——
舊記錄裡的 `notes` 寫著該期實際交叉驗證過的數字，`sha256` 也綁定該期的原始檔。

自動新增的記錄 `verification` 一律記為 `unverified`：排程做得到自我驗證與幅度檢查，
做不到跨來源的人工核對（例如與原民會月報比對）。人工核對過後才改記。

手動執行同一套步驟：

```sh
python scripts/register-period.py register 11507   # 先登記，轉檔腳本才接受該 sourceId
python scripts/fetch-raw.py moi-odrp013-11507      # 取原始檔（分頁逐頁合併）
python scripts/fetch-raw.py moi-odrp018-11507
python scripts/register-period.py seal 11507       # 由原始檔補上雜湊
pwsh scripts/build-population.ps1 -Period 11507    # 轉檔（含自我驗證與幅度檢查）
```

### 回歸測試

```sh
pwsh tests/run-regression.ps1
```

成功時狀態碼 0，失敗時非零並指出失敗的斷言名稱。測試在暫存目錄中執行轉檔，
不會動到 `data/processed/`。樣本涵蓋成功路徑與三條失敗路徑（族別加總不符、
平埔兩組結構重複計算、總量跳動超過門檻）。

另涵蓋具名放行的四種情形：只給 `-AcceptLargeChange`、只給 `-OverrideReason`、
兩者並用而放行成功、以及**族別加總不符的樣本在放行狀態下仍須中止**——
最後一項確保放行只鬆綁幅度檢查而不鬆綁自我驗證。

### 權限

刷新流程需要 `contents: write`（提交資料）與 `actions: write`（觸發部署流程），
與 `deploy.yml` 的唯讀權限模型不同。

需要明確觸發部署的原因是：以 `GITHUB_TOKEN` 推送的 commit **不會**觸發其他 workflow 的
`push` 事件（GitHub 的遞迴防護）。若不處理，資料會進版本庫但站台不會更新，而且流程還是綠燈。

## 資料原則

1. **官方統計、學術估計、本專案計算值三者必須分開標示**，不得混用。
   平埔原住民族人口尤其如此——目前沒有完整官方戶籍統計，任何數字都要標明性質。
2. 資料不足處明確標記為 **Data Gap / 資料缺口**，不自行推估成官方數字。
3. 每個呈現在網站上的數字，都要能在 `data/sources.json` 追到來源。

## 原始檔的入庫與取回

`data/raw/` 裡有兩類東西，性質不同：

- **未加工的下載檔**——五個保留地 CSV、各 XLS、圖資 ZIP。就是機關送出的那一份，未經改動。
- **正規化過的下載**——兩個 ODRP JSON。戶政司的 API 分頁，村里層級 7,771 列分四頁回傳，
  這兩個檔案是四頁合併後由本專案序列化的結果，另帶 `_source`、`_downloadedAt` 等後設欄位。
  合併是取得資料的必要步驟，但它確實不是「原封不動的下載檔」。

**判準是「能不能重新取得」，不是檔案大小。** 可重新取得者不入庫；不可重新取得者入庫，
並在 `.gitignore` 以例外標明理由（目前有兩條：戶政司那份的下載連結由 JS 產生無法程式取得；
原民會月報是第 17 族出現前的最後一期 16 族快照，無法回溯重建）。

不入庫的代價是可稽核性，由 `data/sources.json` 的 `sha256` 欄位補上：

```sh
python scripts/fetch-raw.py                     # 列出可自動取回的來源
python scripts/fetch-raw.py moi-odrp018-11506   # 取回並自動比對雜湊
```

腳本會逐頁取回、合併、計算雜湊並與記錄比對。**雜湊不符時它不會覆蓋你既有的檔案**——
那通常代表來源端更新了資料，該由人判斷要不要接受。

`sha256Kind` 欄位標明雜湊涵蓋的是什麼：未加工的下載檔雜湊**檔案位元組**；正規化過的下載
雜湊**資料內容的正規化形式**（檔中的 `_downloadedAt` 每次取得都不同，位元組雜湊必然不符）。
正規化的確切方式寫在 `sources.json` 的 schema 說明裡，不使用本專案腳本也能重現。
