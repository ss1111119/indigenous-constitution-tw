# 資料來源評估：內政部社會經濟資料服務平台（SEGIS）

日期：2026-08-11
平台：<https://segis.moi.gov.tw/STATCloud/Index>
狀態：**已評估，尚未取用**——本文只記錄查證結果，`data/raw` 與 `data/processed` 目前都還沒有 SEGIS 的檔案。

## 結論：✅ 可用，且補上一個本專案原本沒有的維度

`行政區原住民人口統計` 有**平地原住民／山地原住民**分項，這是戶政司 ODRP013 沒有的
（ODRP013 只到「原住民／非原住民」）。而山地／平地正是兩個原住民立委選舉區的法定分界。

但它**不能替代 ODRP**：沒有族別、沒有平埔欄位、實質為年度資料。定位是補維度，不是補時效。

過程中發現**兩個格式陷阱**，其中一個（`O1`/`O2` 對調）屬於「看似合理但錯誤」那一類，
與 [`data-spine-check.md`](data-spine-check.md) 第二節第 4 項同性質。

## 一、授權：過關

| 項目 | 結論 |
| --- | --- |
| 是否對外公開 | 公開 |
| 只公開特定對象 | 否 |
| 是否需申請 | **不需申請** |
| 再散布 | **允許**（重製、散布、公開傳輸） |
| 依據 | 行政院《政府資訊開放授權條款》，見平台〈資料使用規範〉 |
| data.gov.tw 上的同批資料 | **政府資料開放授權條款第 1 版**（例：[dataset 18650](https://data.gov.tw/dataset/18650)） |
| 附帶義務 | **必須註明來源**「社會經濟資料服務平台」或資料供應機關，未註明視為未獲授權 |

⚠️ **「須申請資料」是完全不同的一類**，平台規範明文「不得再將公開需申請資料轉授權他人」。
查詢介面的「開放程度」有「開放資料／須申請資料」兩個勾選框，**取用前務必確認該資料集的
`是否需申請` 為「不需申請」**，不能因為同一個平台就假設授權相同。

平台頁尾寫的是 `© ... All Right Reserved`，那是網站本身的著作權宣告，
與資料集的開放授權是兩件事，不要因此誤判為不可用。

## 二、取用方式與自動化限制

### 開放服務端點（實測可用）

```
https://segisws.moi.gov.tw/STATWSSTData/OpenService.asmx/GetAdminSTDataForOpenCode?oCode=<code>
```

2026-08-11 於瀏覽器外、**未帶任何 cookie 的情況下實測**：HTTP 200，回傳 JSON。
村里級那份 2,962,405 bytes、7,751 列，一次取回，無分頁。
另供 XML、GeoJSON(TWD97)、GeoJSON(WGS84)、CSV、SHP。

回應結構為三個頂層鍵：

- `Info` — 後設資訊（`InMetaDatCode`、`InSTUnitCode`、`OutTotal`）
- `ColumnList` — 欄位定義（`COLUMN_NAME` / `DATA_TYPE` / `COLUMN_DESC`）
- `RowDataList` — 資料列

**`ColumnList` 帶有中文欄位說明，這是它比 ODRP 好的一點**——欄位語意隨資料同時取得，
不必另外查格式文件。但見第四節，欄位說明的**排列順序**不可信。

### ⚠️ `oCode` 不可推導，這是自動化的主要障礙

`oCode` 是每個「資料集 × 期別 × 空間單元 × 空間範圍」各一組的 96 位十六進位碼，
**沒有 `?period=` 這類參數**。無法像 ODRP 的 `/ODRP018/11507` 那樣直接組出下一期網址。

這與可行性報告待辦 4 記錄的「原民會月報 16 位隨機 ID 不可推導」是同一個病。

可走的路：data.gov.tw 的資料集頁會列出當期全部資源網址（dataset 18650 有 44 條），
從那裡取 `oCode` 清單再取數。**尚未驗證** data.gov.tw 是否提供該清單的機器可讀介面，
以及新期別上架時舊 `oCode` 是否失效——要納入自動更新前必須先確認這兩件事。

## 三、兩份資料集

以關鍵字「原住民」查詢，空間統計單元可選縣市／鄉鎮市區／村里／二級發布區／一級發布區／
最小統計區／三至六級網格。與本專案相關的是這兩份：

### A. `行政區原住民人口統計` ★ 重點

權責單位：內政部統計處。空間單元：縣市／鄉鎮市區／村里三級。格式 CSV／SHP。

| 欄位 | 說明 |
| --- | --- |
| `O_CNT` / `O_M_CNT` / `O_F_CNT` | 原住民人口數／男／女 |
| `O1_CNT` / `O1_M_CNT` / `O1_F_CNT` | **平地原住民**／男／女（見第四節，不可依順序判斷） |
| `O2_CNT` / `O2_M_CNT` / `O2_F_CNT` | **山地原住民**／男／女（同上） |
| `NON_O_CNT` | 非原住民人口數 |
| `INFO_TIME` | 資料時間，格式 `114Y12M` |
| `COUNTY_ID` / `COUNTY` / `TOWN_ID` / `TOWN` / `V_ID` / `VILLAGE` | 行政區代碼與名稱 |

**為什麼重要：** 憲法增修條文第 4 條的原住民 6 席分為山地 3 席、平地 3 席。
本站選舉面板目前寫「原住民立委選舉區為山地、平地兩個全國性選區，無法依縣市切分」——
選區本身確實沒有地理邊界，但**選民的居住分布**這份資料給得出來。
席次模擬器若要處理山地／平地的分別配置，這也是唯一的官方基數來源。

### B. `行政區原住民人口指標` — 用處有限

同單位、同三級空間單元。欄位只有比率：`O_PER` 原住民人口比率、`O_DEPENDENCY_PER` 扶養比、
`O_A0A14_A15A65_PER` 扶幼比、`O_A65UP_A15A64_PER` 扶老比、`O_A65_A0A14_PER` 老化指數。

**沒有人數。** 比率都能從 A 自行計算，而且自行計算才符合本專案「計算值須標為
`derived-by-this-project`」的紀律。它唯一獨有的是年齡結構指標，邊際價值低。

## 四、兩個格式陷阱

**兩項都是實測踩到的，不是理論風險。**

### 1. ⚠️ `O1` = 平地、`O2` = 山地，且**不可依欄位順序判斷**

metadata 頁面上兩處敘述**互相矛盾**：

- 「資料集摘要」的敘述順序：原住民 →**平地**→ 山地 → 非原住民
- 「資料欄位清單」的顯示順序：原住民 →**山地**→ 平地 → 非原住民

兩者不可能同時正確，因此**順序完全不能當判準**。

**判定方法（用族群結構反推，可重現）：**

| 縣市 | 原住民總數 | `O1_CNT` | `O2_CNT` | 主要族群 | 法定身分別 |
| --- | --- | --- | --- | --- | --- |
| 屏東縣 | 63,137 | 5,743 | **57,394**（91%） | 排灣、魯凱 | 山地 |
| 南投縣 | 30,144 | 2,039 | **28,105**（93%） | 賽德克、布農、泰雅 | 山地 |
| 新竹縣 | 23,508 | 3,612 | **19,896**（85%） | 泰雅 | 山地 |
| 花蓮縣 | 94,924 | **57,156**（60%） | 37,768 | 阿美 | 平地 |
| 臺東縣 | 79,340 | **55,835**（70%） | 23,505 | 阿美、卑南 | 平地 |

→ **`O1` = 平地原住民、`O2` = 山地原住民**（即「資料集摘要」的順序正確，
「資料欄位清單」的顯示順序會誤導）。

全國總量再驗一次：`O2`（山地）335,470，對照排灣＋泰雅＋布農＋太魯閣＋魯凱＋賽德克＋鄒＋
賽夏約 33.1 萬，吻合；`O1`（平地）293,986，阿美族約 21.5 萬為主體，合理。

**搞反的後果：** 不會報錯、總數也正確（`O1+O2` 恆等於 `O_CNT`），只會產出一張
山地與平地完全對調的地圖——屏東變成平地原住民大縣、花蓮變成山地原住民大縣。
這正是 `data-spine-check.md` 所說「看似合理但錯誤」的類型。

**若要取用，轉檔腳本必須內建這條自我驗證**：屏東縣的山地原住民應佔該縣原住民九成以上。
不要相信欄位順序，也不要相信未來版本的欄位說明不會再對調一次。

### 2. ⚠️ 村里級資料的 `TOWN_ID` 欄位是壞的

村里級 7,751 列中，**7,218 列（93%）的 `V_ID` 前綴對不上 `TOWN_ID`**。

追下去發現不是兩套編碼慣例，是欄位本身有問題：

| 檢查項 | 結果 |
| --- | --- |
| `TOWN_ID` 相異值 | **22**（＝縣市數） |
| `V_ID` 前綴相異值 | **368**（＝全臺鄉鎮市區數） |
| 一個 `V_ID` 前綴對應到多個 `TOWN_ID` | **0**（前綴與鄉鎮 1:1） |
| 一個 `TOWN_ID` 對應到多個 `V_ID` 前綴 | 22（即全部） |

例：高雄市新興區各里的 `TOWN_ID` 全部是 `64000190`，但 `V_ID` 是 `64000060-017` 等；
而前綴 `64000060` 只出現在新興區。也就是說**每個縣市的所有村里被填上同一個鄉鎮代碼**。

**結論：`TOWN_ID` 不可使用，真正的鄉鎮代碼是 `V_ID` 的前綴（`V_ID.split('-')[0]`）。**
直接拿 `TOWN_ID` 做 join，會把整個縣市的村里全部歸進同一個鄉鎮。

（`TOWN` 名稱欄位本身是正確的，錯的只有代碼欄位。但用中文名稱做 join 是另一種地雷，
仍應改用 `V_ID` 前綴。）

## 五、驗算

縣市級 `行政區原住民人口統計`（`114Y12M`，22 列）：

| 檢核 | 結果 |
| --- | --- |
| 男 304,386 ＋ 女 325,070 | ＝ 629,456 ＝ `O_CNT` ✅ |
| 平地 293,986 ＋ 山地 335,470 | ＝ 629,456 ✅ |
| 平地男 142,962 ＋ 平地女 151,024 | ＝ 293,986 ✅ |
| 山地男 161,424 ＋ 山地女 174,046 | ＝ 335,470 ✅ |
| 縣市數 | 22 ✅ |
| 原住民 629,456 ＋ 非原住民 22,475,916 | ＝ 23,105,372（全國人口，合理） |

**獨立外部對照：** 內政部〈115 年第 8 週內政統計通報〉標題即為
「114 年底原住民人口數 **62.9 萬人**，較 113 年底增加 2.9%」，與 629,456 相符。
這是與本平台不同管道的官方發布，構成有效交叉驗證。

**與本專案既有資料的關係：** 本站現用 ODRP018 為 `115Y06`（2026-06）的 637,620。
SEGIS 這份是 `114Y12M`（2025-12）的 629,456，半年增加 8,164 人，與年增 2.9% 的速率相符。
**兩者期別不同，不可互相取代，也不可放在同一張圖上比較而不標示基準日。**

⚠️ **待驗證的差異：** SEGIS 村里級為 **7,751 列**，而 `sources.json` 記載 ODRP018 為
**7,771 列**，相差 20。可能來自期別不同造成的村里增併、或兩者對「村里」的認定範圍不同
（例如是否含未編村里之區域）。**取用村里級資料前必須釐清**，否則兩來源的村里無法對接。

## 六、它幫不上的地方

1. **沒有族別，更沒有平埔族群欄位。** 只有原住民／平地／山地／非原住民四類。
   `gap-pingpu-household-population` 完全沒有被填補。
2. **更新頻率標示為「不定期更新」，實質是年度（各年 12 月底）。**
   ODRP018 是月報。**因此 SEGIS 無法用來追蹤西拉雅族的逐月身分登記數**——
   那件時效最關鍵的事仍然只能靠 ODRP018。
3. 因此它與 ODRP 的分工是：**SEGIS 給「山地／平地」與「村里粒度」，ODRP 給「時效」與「族別」。**
   兩者不重疊、不互相取代。

## 七、若要取用，建議的順序與注意事項

1. 先收 `行政區原住民人口統計` 的**縣市與鄉鎮市區**兩級。村里級 2.9MB 對前端過重，
   若要收僅進 `data/raw`，不進發佈目錄。
2. 轉檔腳本必須實作第四節的兩條自我驗證（屏東山地佔比 ≥ 90%；不使用 `TOWN_ID`），
   驗證失敗即中止不產檔——沿用 `build-population.ps1` 既有的作法。
3. 前端若呈現，須標明基準日為民國 114 年 12 月底，**與人口面板的 115 年 6 月底不同期**。
4. 依授權規定，來源標示須出現「社會經濟資料服務平台」或「內政部統計處」。

## 八、尚未驗證

- data.gov.tw 是否提供 `oCode` 清單的機器可讀介面；新期別上架後舊 `oCode` 是否失效。
- SEGIS 7,751 村里 vs ODRP018 7,771 列的 20 列差異來源（見第五節）。
- 鄉鎮市區級資料是否也有 `TOWN_ID` 的同類問題（本次只檢查了村里級）。
- GeoJSON 供應的界線精度與 `data/geo/` 現有圖資是否一致；若一致，或可取代
  `scripts/build-geo.py` 的一部分工作。
- 「身分別」（平地／山地原住民）與「族別」的關係：兩者是不同法律概念，
  阿美族並非全部登記為平地原住民。若要把 SEGIS 的身分別與 ODRP018 的族別並陳，
  須先確認這層對應關係，不可推定為一對一。
