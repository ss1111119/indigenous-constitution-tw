**(1) 席次問題是法定待決事項，不是假設性議題。**

立即適用，但**政治參與權明文留給三年內的後續立法**。也就是說「平埔族人要不要有立委保障

從「有趣的假設練習」變成「對正在進行中的立法辯論提供數據基礎」。

**現在是官方數字誕生前的最後時刻**。

原民會副主委杜張梅莊表示，未來三年需調整的法律、法規或行政命令有 **118 條**，預計

### 判斷

**Existing projects cover 人口分布視覺化（中研院，做得很好）、單次選舉制度解釋（報導者）、
保留地與傳統領域圖資（政府圖台），but do not integrate：**

- **A. 人口比例 ↔ 席次比例的代表性計算**（每席代表多少選民、席次占比與人口占比的落差）
  ——中研院做人口不碰選舉，報導者碰選舉但只做單屆敘事，沒有人做跨屆的代表性指標。
- **B. 2025 年平埔身分法之後的制度變動**——所有既有網站都建立在「16 族」的世界觀上，
  包含行政院自己的國情簡介頁。**沒有任何一個網站反映 2026-07-30 之後的第 17 族現實。**
- **C. 制度模擬**——完全沒有人做。「若平埔族人口進入保障體系，席次數學會怎麼變」
  這個問題目前只存在於立法院公聽會記錄與 PDF 裡。

**沒有找到任何 GitHub / GitHub Pages 專案在做這個題目。** 搜尋到的台灣開放資料相關
repo（OpenData-TW、ntuaha/TWVoteData、Vipcube/opendata.gov.tw 等）都是通用型爬蟲或
資料鏡像，沒有原住民主題的整合視覺化。

官方）」與「族群總人口推估（5 萬，非官方）」兩個數字。兩者差距在頭一兩年會非常大，
把它們畫在同一條線上會嚴重誤導。**建議：登記數用實線，推估值用虛線或水平參考線，
且圖上永遠標註「登記自 2026-08 起算」。**

## E. GitHub Pages 技術方案

### 推薦：**Option A（純 HTML + CSS + JavaScript）**

理由：

1. **本站的互動複雜度集中在一個元件**——席次模擬器。那是幾個滑桿加一組算式，
   狀態量小到用不著框架的狀態管理。為了一個模擬器引入 React 是本末倒置。
2. 其餘頁面是圖表 + 說明文字，本質是靜態文件。
3. 無 build step ＝ 無 CI、無 node_modules 版本腐爛、GitHub Pages 直接吃 `/docs` 或
   `gh-pages` 分支。這種公共議題型網站的生命週期以年計，**維護成本比開發爽度重要**。
4. SEO：純靜態 HTML 天生可索引，不需要 SSR/預渲染。

若日後模擬器複雜到需要多參數聯動與分頁狀態，再局部引入 [Alpine.js] 或改 Astro，
屆時遷移成本也低。**不建議一開始就上 Vite + React/Vue。**

### 視覺化函式庫

| 需求 | 推薦 | 理由 |
| --- | --- | --- |
| 長條／折線／堆疊 | **Chart.js** | 體積小、API 直覺、RWD 內建。本站圖表都是常規型 |
| 席次模擬器的席次圖 | **手寫 SVG** | 113 個小方塊的議會座位圖，用任何函式庫都比手寫麻煩 |
| 地圖 | **Leaflet + GeoJSON** | 體積小於 MapLibre，本站不需要向量瓦片與 3D |

不建議 D3（本站沒有需要自訂座標系的圖，殺雞用牛刀）、
不建議 ECharts / Plotly（單檔 1MB 起跳，對只畫幾張常規圖不划算）。

### Repository 結構

沿用已建好的骨架即可（`data/raw` → `scripts` → `data/processed` → 前端讀 JSON）。
前端目錄建議 `docs/`（GitHub Pages 可直接指向），但這會與現有 `docs/` 研究文件衝突，
**建議改為研究文件移到 `research/`、`docs/` 留給網站**。此決定留到 `/spectra-propose` 時定案。

### 資料更新機制：推薦 **方法 A（下載後轉 JSON 入庫）**，局部搭配 **方法 B**

| 方法 | 穩定性 | 政府 API 變動風險 | GH Pages 相容 | 維護成本 | 評 |
| --- | --- | --- | --- | --- | --- |
| A. 手動下載轉 JSON 入庫 | 🟢 最高 | 🟢 無（快照已入庫） | 🟢 | 🟡 中 | ✅ **推薦** |
| B. GitHub Actions 定期抓 | 🟡 | 🔴 來源改版就靜默失敗 | 🟢 | 🟡 | 🟡 僅用於西拉雅登記數 |
| C. 前端直接呼叫政府 API | 🔴 | 🔴 高 | 🔴 **CORS 幾乎必死** | 🟢 | ❌ 排除 |
| D. 全手動 | 🟢 | 🟢 | 🟢 | 🔴 | ❌ |

關鍵理由：**本站資料多為年度或月度更新，即時性不重要，但可稽核性極重要。**
把快照連同下載日期一起 commit 進 repo，等於自帶版本history——三年後有人質疑某個數字，
可以 `git log` 追出當時的來源檔。這對一個處理爭議性議題的網站是必要的。

例外：西拉雅登記人數若原民會提供穩定的月報格式，值得用 Actions 每月抓一次（方法 B），
因為那是本站唯一真正需要「跟上」的數列。

## F. MVP（差異化定義）

**原構想的 MVP「人口＋選舉＋保留地＋基本席次模擬」太大，而且前三項都是別人做過的。**

建議 MVP 收斂成單一頁面，回答單一問題：

> ### 「原住民族在立法院的代表性，現在是多少？如果平埔族群納入，會變成多少？」

包含四個區塊：

1. **現況數字**：原住民族人口 / 全國人口 = X%；6 席 / 113 席 = 5.31%；落差 Z 個百分點。
   每席原住民立委代表 N 位選民，區域立委平均代表 M 位。
2. **時間軸**：憲判17號 → 身分法 → 西拉雅核定 → 三年立法期限。附法規原文連結。
   （這一塊純 HTML，成本極低，但目前網路上找不到第二個地方有完整整理。）
3. **席次模擬器**：滑桿調整「平埔族納入人口數」與「保障席次數」，即時顯示代表性指標變化。
   預設值不預設立場——初始狀態就是現況（Scenario A），使用者自己動手。
4. **資料來源與方法**：每個數字可點開看來源、日期、性質（官方／估計／本站計算）。

**刻意不做的**（列出來避免日後重新盤點）：
GIS 地圖、各族人口分布圖、保留地視覺化、遷徙、部落——全部外連中研院與政府圖台。
土地資料完全不進 MVP：保留地與代表性的關聯需要額外論證，而且平埔族群土地權
根本還沒立法，現在做只能做出一個和主論述無關的漂亮圖表。

MVP 只需要三個資料集：原民會人口月報、中選會歷屆立委選舉、內政部全國人口數。

## 十五、最重要的研究問題：現在做還有沒有資訊價值？

逐題回答：

**1. 網路上是否已經有同類產品？**
沒有完整同類產品。有三個部分重疊者：中研院 CAPAS（人口視覺化）、報導者（選舉制度解釋）、
政府圖台（土地 GIS）。三者互不連通，且都不處理代表性計算。

**2. 哪些資料已經被充分視覺化？**
人口分布（中研院做到 10K 點陣，一點代表一人，品質很高）、部落點位、保留地範圍圖資。
**這三塊不要重做。**

**3. 哪些資料目前很分散？**
選舉。中選會有完整原始資料，但要理解「原住民立委代表性」必須自己跨屆下載、
自己對應選舉區、自己算比例。報導者做過一次，但是 2020 年的靜態圖，且未更新至 2024。

**4. 哪些資料目前要使用者自己下載 Excel 才能理解？**
原民會人口月報（XLS）、保留地筆數面積（CSV）、中選會 votedata.zip。
**尤其是「每席原住民立委代表多少選民」這個數字，目前不存在於任何網頁上，
必須自己下載兩份不同機關的檔案才能算出來。**

**5. 哪些資料目前沒有被整合？**
人口 × 選舉 × 憲政席次。完全沒有。

**6.「人口＋土地＋選舉＋憲政代表性」是否是缺少的整合視角？**
部分是。誠實地說：**土地那一塊是湊數的**——它與代表性的邏輯關聯最弱，
且平埔族群土地權尚未立法。真正缺少的整合視角是「**人口 × 選舉 × 憲政代表性**」三者。
建議把土地降為第二階段。

**7. 是否有研究、教育、媒體或公共議題溝通價值？**
有，而且時間點罕見地好。三年立法期限（至 2028-10）內，關於平埔族群政治參與權的
討論一定會發生，屆時所有人都會需要一個「數字長什麼樣」的參考點。
現在沒有人提供這個參考點。

### 最終結論：🟢 值得做

但成立條件有三個，缺一則降為 🟡：

1. **範圍必須收斂成 F 節的 MVP**，放棄與中研院、政府圖台正面競爭。
2. **必須嚴守官方／估計／本站計算的三分法**。這個題目政治敏感度高，
   一旦把「5 萬人」這種專家推估寫成官方數字，整站可信度歸零。
3. **必須真的維持更新**，至少撐過 2028 年 10 月的立法期限。一個停在 2026 年的
   代表性網站，價值會隨立法進度衰減到零。
