## Context

`site/js/main.js` 在分頁切換後執行 `refreshVisiblePanel()`，重算剛顯示出來的面板中的圖表版面。分頁以 CSS `display` 切換，非作用中的面板寬度為 0，因此圖表在隱藏狀態下建立時版面是錯的，顯示後必須重算。

該函式對 Chart.js 的處理是直接的：找出可見面板中的每個 canvas，取得對應的 chart 實例，`resize()` 後接 `update('none')`。對 Leaflet 的處理則是發出全域 `window resize` 事件，讓 Leaflet 自己的 resize 處理器去量測。

兩者的差別在於精確度。Chart.js 那條路徑明確指定了對象；Leaflet 那條路徑是廣播，接收者包含頁面上每一個 Leaflet 實例與每一個 `window resize` 監聽器。

`site/js/panel-map.js` 以模組層級變數持有唯一的 map 實例。`ensureMap()` 在重繪時沿用該實例、只換圖層，並把容器重新 append 回面板；重新 append 之後呼叫量測。這個決策是刻意的——重建實例會重設使用者的平移縮放位置。

已量測到的事實：在容器隱藏（`getBoundingClientRect()` 為 0×0）時觸發 Leaflet 量測，會把其內部尺寸快取寫成 `(0, 0)`；未觸發量測時快取保留隱藏前的值。

限制條件：維持零 npm 相依、不新增測試框架、不動 vendored 函式庫版本。

## Goals / Non-Goals

**Goals:**

- 版面重算只作用於意圖的對象，不經由全域事件廣播。
- 地圖在自己不可見時不執行量測，因而不把零尺寸寫入內部狀態。
- 呼叫端（啟動點）不需要知道 Leaflet 的 API，也不需要知道零尺寸的陷阱。
- 未來新增第二張地圖時，切換分頁不會影響到不相關的地圖。

**Non-Goals:**

- 不追查 `Invalid LatLng object: (NaN, NaN)` 的根因，也不宣稱本 change 修好了它——該錯誤無法穩定重現，見 proposal。
- 不改用 `ResizeObserver` 重做觸發機制。
- 不升級 vendored Leaflet 或 Chart.js。
- 不改動地圖視覺呈現、視野範圍、縮放行為。
- 不改動 `ensureMap()` 沿用單一實例的決策。
- 不改動 Chart.js 的重算路徑。

## Decisions

### 決策一：由地圖模組提供具名入口，不對外暴露 map 實例

`site/js/panel-map.js` 匯出一個具名函式，語意是「若地圖存在且可見，重新量測並修正版面」。map 實例維持模組私有。

替代方案是直接 export map 實例，讓 `main.js` 自己呼叫 Leaflet API。否決原因：呼叫端就必須知道 Leaflet 的方法名稱、知道零尺寸時不能量測、知道實例可能還不存在。這三件事都是地圖模組的內部知識，外洩出去等於把一個模組的責任散到啟動點；日後改動地圖實作就得同時改啟動點。

具名入口讓呼叫端只表達意圖（「這個面板剛顯示出來了」），怎麼做由地圖自己決定。

### 決策二：可見性判斷放在地圖模組內，不放在呼叫端

「容器尺寸為零就不量測」這條規則寫在 `panel-map.js`。

替代方案是讓 `main.js` 先判斷面板可見再呼叫。否決原因：`main.js` 已經用 `getComputedStyle` 找出可見面板，但那是面板層級的判斷，而地圖容器可能因為別的原因尺寸為零——重繪過程中容器曾脫離 DOM，此時面板是可見的、容器卻沒有尺寸。判斷點必須貼著被保護的對象，否則會漏。

同時這讓保護對所有呼叫路徑生效，包含 `ensureMap()` 自己在重繪時的量測，而不只是分頁切換那一條。

### 決策三：地圖尚未建立時為無操作，不拋錯

初始渲染是非同步的（要取得 GeoJSON），使用者可能在地圖建立之前就切換分頁。此時入口函式直接返回。

替代方案是拋錯或記錄警告。否決原因：這不是異常狀態，是正常的競速結果。拋錯會被 `refreshVisiblePanel` 之外的程式看到；記錄警告會在正常操作下產生雜訊，讓真正的警告被淹沒。

### 決策四：不寫「錯誤不再出現」這種驗收條件

驗收條件全部針對可觀察且可重複的行為：是否仍發出全域 resize、切回分頁後版面是否正確、零尺寸時是否跳過量測。

替代方案是把「連續切換分頁時 console 無 `Invalid LatLng` 錯誤」列為驗收條件。否決原因：該錯誤本來就無法穩定重現，這條件在修正前後都會「通過」，因此不具鑑別力——它只會給人一種驗證過的錯覺。無法重現的缺陷不能用「沒看到」當作修好的證據。

## Implementation Contract

**行為**

- 切換到含地圖的分頁後，地圖佔滿其容器且投影正確，與不曾隱藏過時的呈現一致。
- 切換分頁不再產生 `window` 的 `resize` 事件。
- 地圖容器尺寸為零時，Leaflet 的內部尺寸快取不被改寫為零。
- 地圖尚未建立時切換分頁不產生任何錯誤或警告。
- 其他三個面板的圖表重算行為不變。

**介面**

- `site/js/panel-map.js` 匯出一個具名函式，無參數，無回傳值，語意為「重新量測地圖並修正版面，若地圖不存在或容器尺寸為零則不做任何事」。map 實例不匯出。
- **【實作時補充】跳過視野調整必須配一個延後套用的機制。** 「零尺寸時跳過」若等於「不做」，會產生可見的錯誤：使用者在別的分頁改變地區時，圖層已換成新地區、視野仍框著舊地區，切回來就是錯的框。因此模組內以一個旗標記錄「視野尚未套用」，於容器取得尺寸後（即上述匯出函式被呼叫時）補做，成功套用後清除旗標。這不是新增的行為，而是既有 spec scenario「a map is laid out correctly after its panel is shown again」中「matching how it renders when it was never hidden」所要求的；原設計只寫了跳過，沒寫出補做的機制。
- `site/js/main.js` 的 `refreshVisiblePanel()` 在可見面板含有 Leaflet 容器時呼叫該函式，取代原本的全域事件派發。其 Chart.js 分支不變。

**失敗模式**

- 地圖不存在 → 無操作，無錯誤、無警告。
- 容器尺寸為零 → 跳過量測與視野調整，不改寫尺寸快取，無錯誤、無警告。
- 上述兩者皆為預期狀態，刻意靜默；靜默的理由是它們在正常操作下就會發生。

**驗收條件**

- 在 `site/js/` 全目錄搜尋 `dispatchEvent` 與 `new Event('resize')`，無任何結果。
- 於瀏覽器安裝一個 `window` 的 `resize` 監聽器並計數，切換全部四個分頁各一次，計數維持 0。
- 依序切到選舉、土地、席次模擬，再切回人口面板，地圖寬度等於其容器寬度（誤差 1 像素內），且地圖可正常平移縮放。
- 在地圖所在面板隱藏的狀態下呼叫該匯出函式，Leaflet 的 `getSize()` 維持隱藏前的值而非變為 0×0。
- 於頁面剛載入、地圖尚未建立的時點呼叫該匯出函式，無錯誤拋出、console 無新增訊息。
- 選舉、土地、席次模擬三個面板的圖表在切換分頁後版面正確：刻度與資料點對齊，資料點未擠在最左端。

**範圍邊界**

- 在範圍內：`site/js/panel-map.js` 新增匯出入口與零尺寸守衛、`site/js/main.js` 改為呼叫該入口並移除全域事件派發。
- 不在範圍內：`Invalid LatLng` 崩潰的根因追查、`ResizeObserver` 改造、Leaflet 或 Chart.js 版本升級、地圖視覺呈現、`ensureMap()` 的單一實例決策、Chart.js 重算路徑、任何資料或轉檔腳本的改動。

## Risks / Trade-offs

- **零尺寸時跳過量測，可能讓某些時序下地圖始終沒被量測到，表現為版面錯誤而非崩潰** → 分頁切換是每次顯示都會觸發的路徑，顯示後容器必然有尺寸，故顯示時一定會量測到一次。驗收條件納入「切回人口面板後地圖寬度等於容器寬度」正是為了擋這個風險。
- **靜默的無操作會讓真正的問題不易察覺** → 兩種靜默情況都是正常競速結果而非異常，記錄警告只會產生雜訊。若日後懷疑地圖沒被量測，判斷依據是版面本身，而非日誌。
- **本 change 可能完全沒有解決那個 `Invalid LatLng` 崩潰** → 明確接受。proposal 與本文件都不宣稱修好它；若它再次出現且可重現，另開 change 處理。這是刻意不把未驗證的功勞算進來。
- **只有一張地圖時，廣播與指定對象的可觀察差異很小** → 差異在於零尺寸寫入與未來的第二張地圖。驗收以「全域 resize 計數為 0」這個可機械檢查的條件固定下來，不倚賴「看起來一樣」。
