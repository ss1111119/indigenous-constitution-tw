## Context

`data/sources.json` 是本專案的唯一真實來源，逐筆記著 22 個資料來源與 4 個資料缺口。
它已被複製進發佈目錄（`build-site.py` 的必要資料清單含 `sources.json`），
前端的 `provenance.js` 也已在使用它——但只在使用者點開某個數字的溯源彈窗時載入，
且只取用機關、基準日、資料集、授權、性質五個欄位。

其餘欄位（`verification`、`updateFrequency`、`api`、`format`、`sha256`）與
最有價值的 `notes`（含格式陷阱、自動化障礙、授權查證過程、評估後不取用的理由）
在站台上完全沒有出口。

受眾是想使用這些資料的人，不是讀站台數字的一般讀者。

## Goals / Non-Goals

**Goals:**

- 讓 22 筆來源的取得方式、限制與授權狀態對外可讀
- 讓「哪些資料不可自動追蹤」與「哪些資料不可混用」成為可掃視的檢視，而非埋在長段落裡
- 授權呈現不得讓讀者以為可以做超出實際允許範圍的事
- 資料缺口與可使用來源明確分開

**Non-Goals:**

- 不拆 `notes` 成結構化欄位（第二階段）
- 不改 `sources.json` 的既有欄位語意
- 不新增被 fetch 的資料檔
- 不做機器可讀 catalog 或可執行的重現範例（後續變更）

## Decisions

### 頁面完全由資料產生，不手寫任何一筆內容

站台已有一次教訓：`index.html` 的「資料缺口」段落是手寫的、不由 `gaps[]` 產生，
因此 `sources.json` 新增缺口不會出現在任何地方，兩邊可以無聲地不同步。
本頁若手寫 22 筆，同樣的漂移會以更大的規模重演。

因此頁面骨架為靜態 HTML，內容一律於前端由 `sources.json` 產生。
新增來源記錄後不需改動頁面程式。

### 授權必須拆成兩個獨立事實呈現

`license` 記的是**提供者的授權宣告**，`reusable` 記的是**本專案對自身使用的判斷**。
兩者不是同一件事，資料裡已有實例：`cip-monthly-population-11506` 的 `license` 為
「非開放授權」，`reusable` 卻是 `true`——因為本專案依該宣告允許的合理使用範圍，
判斷自己「逐字、未改動、註明出處」的再散布被允許，而同一筆的 `notes` 明確排除
改作、重新編排與去除出處。

只顯示一個「可再利用」結論，會讓讀者以為能拿去改作，而那正是 notes 排除的行為。
故授權區塊須同時呈現兩者，並在兩者不一致時要求讀者讀原文 notes。

`reusable` 的三種值（true / false / unknown）須分別呈現，不得把 `unknown` 併入任一端。

### 自動化狀態由既有欄位導出，不新增欄位

`api` 欄位（17 筆有值）已足以區分「有 API」與「沒有」。至於**為什麼**不能自動追蹤
（隨機 ID、不可推導的 oCode、JS 產生的連結、跨屆變動的欄位），
本次不抽成結構化欄位——那需要逐筆人工判斷，屬第二階段。

本次的自動化檢視以 `api` 為準，並在該筆的原文 notes 中呈現原因。
檢視本身標明「原因見各筆說明」，不假裝已經結構化。

### 原文 notes 完整呈現，預設收合

notes 最長 2,826 字，最短 27 字。全部展開會讓頁面無法掃視，截斷則會失去證據價值——
而 notes 正是這份盤點的價值所在。故預設收合、可展開，且不做任何截斷或改寫。

收合以原生 details 元素實作，不依賴腳本，停用 JavaScript 時仍可展開閱讀。

### 獨立頁面，不併入首頁的分頁切換

首頁是儀表板，四個面板共用一個區域選擇器。資料目錄的閱讀方式完全不同
（長文、需要搜尋與比較），併進分頁會使兩種閱讀模式互相干擾。
且首頁目前刻意不在初始載入 `sources.json`（61KB），併入會破壞這個設計。

故為獨立 URL，首頁加入口連結。

## Implementation Contract

**行為**：讀者開啟目錄頁後，可看到 22 筆來源的表列與 4 筆資料缺口的獨立區塊；
每筆可展開讀到完整原文說明；可看出哪些來源具備 API、哪些不具備；
授權欄位同時呈現提供者宣告與本專案判斷。

**資料介面**：本頁只讀 `data/sources.json`，路徑經由站台既有的資料基底路徑常數取得，
不另行定義路徑。不新增任何資料檔，不修改 `sources.json` 的結構。

**失敗模式**：`sources.json` 載入失敗時，頁面顯示明確的載入失敗訊息並指出缺少的檔案，
與站台既有面板的錯誤處理方式一致；不得以空表或靜默空白呈現。
某筆來源缺少非必填欄位（如 `verification`、`updateFrequency`）時，
該欄顯示為未記載，不得顯示為空白或推測值。

**驗收**：
- 頁面所有內容可追溯至 `sources.json` 的欄位；原始碼中不存在硬寫的來源名稱或授權文字
- 22 筆來源與 4 筆缺口全數呈現，數量與 `sources.json` 一致
- `cip-monthly-population-11506` 一筆同時顯示「非開放授權」與本專案的再利用判斷
- `capas-tpdd`（reusable=false）與 `capas-tipd`（reusable=unknown）呈現方式彼此不同，
  且都與 reusable=true 者不同
- 停用 JavaScript 時，頁面仍說明它需要 JavaScript，且入口連結與標題可讀
- 首頁的初始載入不因本變更包含 `sources.json`

**範圍界線**：
- 範圍內：目錄頁本身、由資料產生的呈現、授權雙軌呈現、缺口分區、首頁入口連結
- 範圍外：notes 結構化、機器可讀 catalog、重現範例、`sources.json` 的欄位變更

## Risks / Trade-offs

- **[61KB 的 JSON 於前端解析]** → 只在本頁載入，首頁不受影響；
  該檔已在發佈清單中，不增加新的網路請求種類。

- **[原文 notes 混雜多個主題，讀者可能只讀到前段]** → 本次接受。
  結構化是第二階段的工作，而截斷或摘要會失去證據價值，比混雜更糟。

- **[「自動化檢視」以 api 欄位為準，可能與實際可自動化程度不完全一致]** →
  檢視明示原因見各筆說明，不宣稱該欄位等同可自動追蹤。
