## Problem

具名放行是「異常資料要不要上線」的最後一道人工關卡，但它在真實 GitHub Actions runner 上
**從未被完整執行過**——至今沒有任何期別的變動超過 ±1%（11506→11507 僅 +0.133%）。
封存的 scheduled-data-refresh design 已把三項列為延後驗證：放行分支本身、百分比擷取的
正規式、commit 訊息追加。

觸發條件正是這個站台存在的理由：西拉雅族身分登記自 2026-08 中開放，
依原民會轉述的學術估計，首批登記可能使單期變動達數個百分點。期別 11508 預計 2026-09 初發布。
也就是說，這條路徑很可能在數週內於生產環境首次被觸發，而那一次沒有第二次機會。

三個具體弱點：

1. **整條路徑掛在中文訊息的字串比對上。** workflow 以 `幅度檢查【已具名放行】` 判斷是否被放行，
   再用正規式從人類可讀的訊息中挖出百分比。轉檔腳本的措辭一改，耦合即斷。
   目前對不上時會 throw，屬大聲失敗而非靜默失敗，但仍是最脆弱的一環。

2. **百分比擷取只在放行時執行。** 那段正規式要處理負數、小數與全形括號，
   卻只會在最需要它正確的那一天第一次運行。

3. **commit 訊息組裝只在「有 diff」時執行。** 以既有期別重跑（產出相同、不提交）
   無法演練組裝，因此在真實的大幅變動發生前，訊息組裝完全無法被觀察。

## Root Cause

放行路徑的每一個環節都只在「變動超過門檻」時才會執行，而該條件在整個開發期間從未成立。
可觀察性被綁在觸發條件上：越是罕見而關鍵的路徑，執行次數越少、被驗證的機會越少。

## Proposed Solution

1. 轉檔腳本輸出穩定的機器可讀標記（放行與否、觀察到的變動百分比），workflow 解析該標記
   而非人類可讀的中文訊息。訊息措辭與流程解析自此解耦。

2. 變動百分比一律擷取，不限放行時。擷取結果寫入流程摘要，使該解析在每一次排程執行中
   都被真實運行。

3. commit 訊息的組裝移出「有 diff」分支，組裝結果一律寫入流程摘要；是否提交仍依 diff 決定。

4. 新增合成資料的訊息渲染驗證，涵蓋正負與小數百分比、含換行的理由、
   訊息須含幅度與完整理由、以及未放行時不得出現放行段落。

## Non-Goals

- **不改變 commit 訊息在非放行時的格式。** 每次提交都附上變動幅度會把例行更新混入診斷欄位，
  並使「幅度曾被計算」看起來像「曾被放行」。幅度只進流程摘要。
- **不放寬或調整 ±1% 門檻，也不新增任何調整門檻的途徑。** 現行規格明訂不提供，本變更不碰。
- **不以合成資料觸發真實的資料提交。** 渲染驗證只驗訊息組裝，不產生任何會被提交的資料。
- **不做平埔登記逐月時序保存。** 屬獨立變更，且目前各期平埔皆為零，尚無真實資料可驗證設計。

## Success Criteria

- workflow 判斷是否放行、以及取得變動百分比，均不依賴轉檔腳本輸出的中文訊息措辭。
- 每一次成功轉檔的流程摘要都可看到觀察到的變動百分比，無論是否放行。
- 以既有期別手動觸發時，流程摘要可看到組裝出的 commit 訊息，且該次執行不產生提交、不觸發部署。
- 訊息渲染驗證涵蓋正負與小數百分比、含換行的理由，並斷言未放行時訊息不含放行段落。
- 既有行為不變：非放行的排程提交訊息格式與變更前相同；放行時仍記錄幅度與理由。
