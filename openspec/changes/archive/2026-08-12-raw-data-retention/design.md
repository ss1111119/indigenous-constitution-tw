## Context

`data/raw` 已入庫 48MB，其中 `data/raw/moi-odrp018-population-by-tribe-11506.json` 佔 41,471,418 bytes。

`.gitignore` 的原則寫在註解第一行：「原始檔可重新下載，就不入庫」。但實作是按副檔名列舉 xlsx、xls、zip、shp、dbf、shx、prj、gpkg——**沒有 json**。那個 40MB 檔案因此進了版本庫，不是有人衡量後的決定。

已實測的事實（2026-08-11）：

- `https://www.ris.gov.tw/rs-opendata/api/v1/datastore/ODRP018/11506` 與 `/11507` 皆回 HTTP 200，回應中的 `statistic_yyymm` 欄位對應所請求的期別，期別代換有效。
- 該 API 分頁：`totalPage` 為 4、`pageDataSize` 為 2000、`totalDataSize` 為 7771（11506）與 7781（11507）。單次呼叫只回 2000 列。
- `11507` 已上架。ODRP018 是月報，維持現狀則每期再增約 40MB。

**兩個 ODRP JSON 不是原始下載檔。** 兩者的頂層結構為 `_source`、`_dataset`、`_agency`、`_statistic_yyymm`、`_downloadedAt`、`_note`、`data`——四頁合併後由本專案序列化，另加六個後設欄位。五個保留地 CSV 與各 XLS 則是真正未加工的下載（CSV 仍帶 BOM 與原始欄名）。

`data/sources.json` 目前沒有任何雜湊或校驗欄位。因此連已被忽略、未入庫的 `data/raw/cec-votedata.zip`（110MB）也無從驗證版本。

## Goals / Non-Goals

**Goals:**

- 止住 `data/raw` 隨月報成長的軌跡。
- 可稽核性不因不入庫而受損：他人能取得同一份資料並確認無誤。
- 「可重新取得」是一個可執行的動作，不是一句宣稱。
- `.gitignore` 的規則與它自己宣示的原則一致。

**Non-Goals:**

- 不重寫 git 歷史。
- 不更新資料期別到 11507。
- 不重新分類 `data/raw`（改以更正 README 敘述處理）。
- 不改動 `data/processed/`、`data/geo/` 的入庫方式。
- 不引入 Git LFS 或外部物件儲存。
- 不改動面板行為、資料內容或發佈流程。

## Decisions

### 決策一：止血而非手術——停止追蹤，不重寫歷史

以 git 的 cached 移除停止追蹤兩個 ODRP JSON，既有 blob 留在歷史中。

替代方案是重寫歷史徹底移除。否決原因：40MB 在 GitHub 的所有限制之下，整個 repo 才 48MB，clone 成本是幾秒鐘；而重寫公開版本庫的歷史會讓既有的 clone 與 fork 失效，需要通知所有下游。**問題在軌跡不在現況**——一顆 40MB 的舊 blob 可以忍，每年十二顆不行。用最小的動作解決真正的問題。

若日後歷史體積真的成為問題，那是獨立且需要協調的操作，不該夾帶在策略變更裡。

### 決策二：雜湊的對象視檔案性質而異，不是一律雜湊位元組

兩類檔案分別處理，`data/sources.json` 的 schema 必須標明用的是哪一種：

- **未加工的下載檔**（CSV、XLS、ZIP）：雜湊**檔案位元組**。它們就是政府送出的那份，位元組穩定。
- **本專案正規化過的下載**（兩個 ODRP JSON）：雜湊**資料內容的正規化形式**——對 `data` 陣列以固定的序列化參數（鍵排序、不轉義非 ASCII、無多餘空白）產生字串再取雜湊。

替代方案是一律雜湊檔案位元組。**否決原因：對 ODRP JSON 行不通。** 檔案含 `_downloadedAt`，每次重新取得都會變；四頁合併後的序列化結果又受鍵序、空白、跳脫設定影響。位元組雜湊會在每次重新取得時失敗——那是一個永遠紅燈的檢查，比沒有檢查更糟。

正規化雜湊驗的是「你拿到的資料與本站用的是同一份」，而不是「你的檔案與我的檔案位元組相同」。對一個會嵌入下載日期的格式，後者本來就不可能成立，而前者才是稽核真正關心的事。

### 決策三：重新取得腳本必須實際跑得動，且自動比對雜湊

新增 `scripts/fetch-raw.py`，能重新取得兩個 ODRP 資料集：依 `totalPage` 逐頁抓取、合併為單一 `data` 陣列、產生與現有檔案相同結構的輸出，並計算正規化雜湊與 `data/sources.json` 的記載比對。

替代方案是只在文件裡寫下 API 網址，讓讀者自己處理。否決原因：該 API 分頁，一次只給 2000 列中的 7,771 列。只給網址的人會拿到四分之一的資料而不自知——**那不是「可重新取得」，是把重建成本連同一個陷阱丟給別人**。腳本的存在本身就是「可重新取得」這個主張的證據。

腳本不下載 `cec-votedata.zip`（110MB，非 API、無分頁問題），該檔的雜湊僅供人工比對。

### 決策四：`.gitignore` 的註解改為明講依據，不列舉副檔名

現有規則按副檔名列舉，而那正是 40MB 檔案漏網的原因——新增一種格式就漏一種。改為在 json 規則旁明寫判準：**可重新取得者不入庫；不可重新取得者以例外標明並附理由。**

現有兩條例外（戶政司 xls 需人工點擊、原民會月報為 16 族結構的最後一期快照）的寫法很好——它們都附上了「為什麼這一份不適用一般原則」的具體理由，保留不動。

### 決策五：更正 README 對 `data/raw` 的敘述

README 現寫「政府原始下載檔，不做任何修改」。這對 CSV 與 XLS 成立，對兩個 ODRP JSON 不成立。改為描述實情：該目錄含未加工的下載檔，以及分頁 API 取得後合併的正規化下載，後者另帶記錄來源與取得日的後設欄位。

替代方案是把 ODRP JSON 移出 `data/raw` 讓目錄名副其實。否決原因：那兩個檔案即將不再入庫，移動一個要被移除追蹤的檔案收益很低，且會動到轉檔腳本的輸入路徑。合併分頁是取得資料的必要步驟而非加工，稱為原始下載並不離譜——只要文件說清楚。

## Implementation Contract

**行為**

- `git ls-files data/raw` 不再列出兩個 ODRP JSON，且該指令列出的檔案總量顯著下降（由約 48MB 降至約 4MB 量級）。
- 兩個 ODRP JSON 仍存在於本機工作目錄，轉檔腳本照常可用；`git status` 不再顯示它們（被 ignore 規則涵蓋）。
- `data/sources.json` 中每個對應到 `data/raw` 下實體檔案的來源記錄，都帶有非空的雜湊值與一個標明雜湊種類的欄位。
- 執行重新取得腳本可取得完整資料（7,771 列，非 2,000 列），並自動回報雜湊比對結果。
- 發佈目錄的內容與網站行為完全不變。

**介面**

- `scripts/fetch-raw.py` 接受資料集識別碼（對應 `data/sources.json` 的 `id`）作為參數，不帶參數時列出可取得的識別碼。成功時以狀態碼 0 結束並印出取得的列數與雜湊比對結果。
- `data/sources.json` 的 schema 新增兩個欄位：一個記錄雜湊值，一個記錄雜湊的計算方式（檔案位元組或資料內容正規化）。
- **【實作時修正】雜湊欄位是「檔名 → 雜湊值」的物件，不是字串。** 原本寫「兩者皆為字串」，未考慮一筆來源對應多個實體檔案的情況——`cip-monthly-population-11506` 對應 6 個 xls（縣市／鄉鎮 × 族別／年齡，另加原住民族地區人口與都市比），其餘 17 個檔案為 1:1。若為 1:1 用字串、1:多用物件，就會出現同一欄位兩種型別，那正是本專案先前在 `reusable` 欄位踩過的坑（bool 與字串混用）。**一律用物件**，鍵為 `data/raw` 下的檔名。計算方式欄位維持字串，因為它是整筆來源的性質，不隨檔案而異。
- 正規化雜湊的計算方式必須寫在 schema 的說明中，讓不使用本腳本的人也能重現：對 `data` 陣列以鍵排序、不轉義非 ASCII、逗號與冒號後無空白的方式序列化為 UTF-8 位元組後取 SHA-256。

**失敗模式**

- 重新取得時雜湊不符 → 以非零狀態碼結束，同時印出期望值與實際值，並**保留**下載的檔案供人工比對（不自動覆蓋既有檔案）。雜湊不符可能代表來源端更新了資料，那是需要人判斷的事件，不是腳本該自行決定的。
- API 回應的 `totalPage` 與實際取得頁數不符 → 以非零狀態碼結束並回報，不產生不完整的輸出檔。
- 網路失敗 → 以非零狀態碼結束並回報，不產生半成品檔案。
- 未提供識別碼 → 列出可用識別碼後以狀態碼 0 結束，這是正常用法而非錯誤。

**驗收條件**

- `git ls-files data/raw` 的輸出不含 `moi-odrp018-population-by-tribe-11506.json` 與 `moi-odrp013-population-by-indigenous-status-11506.json`；以該清單計算的總量小於 5MB。
- 兩個 ODRP JSON 仍存在於磁碟，且 `git check-ignore` 對兩者皆回報被 ignore 規則涵蓋。
- 對 `data/raw` 下每個實體存在的檔案，都能在 `data/sources.json` 找到對應記錄且其雜湊欄位非空——包含未入庫的 `data/raw/cec-votedata.zip`。
- 執行重新取得腳本處理 ODRP018 的 11506 期別，輸出 7,771 列，且雜湊比對回報相符。
- 以現有的兩個 ODRP JSON 各自重新計算正規化雜湊，結果等於 `data/sources.json` 記載的值。
- 執行 `python scripts/build-site.py` 後 `_site/` 的檔案數與總大小與改動前相同；以靜態伺服器開啟後四個面板與席次模擬器渲染正常。
- README 中不再出現「政府原始下載檔，不做任何修改」這個對兩個 JSON 不成立的敘述。

**範圍邊界**

- 在範圍內：`.gitignore` 規則與註解、停止追蹤兩個 ODRP JSON、`data/sources.json` 新增雜湊欄位與值、新增重新取得腳本、更正 README 對 `data/raw` 的敘述。
- 不在範圍內：重寫 git 歷史、更新資料期別、重新分類 `data/raw`、`data/processed` 與 `data/geo` 的入庫方式、Git LFS 或外部儲存、任何面板行為與發佈流程的改動。

## Risks / Trade-offs

- **停止追蹤後，若政府端下架該期別，資料就真的取不回來了** → 這是本方案的核心取捨，明確接受。緩解有三：既有的 blob 仍在 git 歷史中（未重寫），本機工作目錄仍有檔案，且雜湊讓任何持有副本的人能證明其為同一份。`.gitignore` 的例外機制正是為「確實取不回來」的檔案保留的——原民會月報那條例外就是這樣判斷後留下的。
- **正規化雜湊依賴序列化參數，換一組參數就得到不同的值** → 因此參數必須寫進 schema 說明而非只存在於腳本中；驗收條件要求「不使用本腳本的人也能重現」。
- **重新取得腳本會隨 API 變動而失效** → 失效時它會以非零狀態碼失敗並回報，而不是安靜產出不完整資料。這與 `build-site.py` 與轉檔腳本的既有作法一致：寧可中止，不可靜默。
- **雜湊不符時不自動覆蓋，需要人判斷** → 增加一個人工步驟，但雜湊不符最可能的原因是來源端更新了資料，那本來就該由人決定要不要接受新版本。自動覆蓋會讓資料在無人察覺下改變。
- **README 更正後，`data/raw` 這個目錄名仍不完全精確** → 明確接受，理由見決策五。
