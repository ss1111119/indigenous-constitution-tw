## Context

本站人口資料來自戶政司 ODRP013 與 ODRP018，期別以民國年月編碼（如 `11506` 即民國 115 年 6 月），由 `scripts/build-population.ps1` 以 `-Period` 參數取數並產生 `data/processed/` 下的 JSON。該腳本只用 ODRP 的 HTTP API 與 pwsh 內建功能，沒有 Excel 或 Windows 相依，因此可在 ubuntu runner 上執行。

目前更新完全靠人工：有人記得跑腳本、記得改文案、記得提交。而 ODRP 的發布日不固定、滯後約兩個月，`11507` 於 2026-08-11 實測尚未發布。

三個現狀構成本次改動的約束：

1. `scripts/build-site.py` 的既有設計是「只搬檔案，不做任何轉換、打包或壓縮」，且本機預覽與 CI 走同一支腳本（`site-deployment` 的單一組建路徑要求）。
2. `dashboard-shell` 要求停用 JavaScript 時頁面仍完整可讀，故 `site/index.html` 內的 `.panel-fallback` 與頁尾「資料來源」是靜態標記，不能單靠 JS 渲染。
3. `data/processed/` 的每份 JSON 已帶 `_sourceId`（如 `moi-odrp013-11506`），可對應到 `data/sources.json` 取得 `dataDate`。基準日其實已是機器可讀的，只有頁面上那幾句話還寫死。

## Goals / Non-Goals

**Goals:**

- ODRP 發布新期別後，網站在無人介入的情況下更新到該期別。
- 頁面上陳述的基準日與平埔族群資料狀態，永遠與實際載入的資料一致。
- 自動更新有安全網：資料異常時中止並發出紅燈，而不是把錯誤數字推上線。

**Non-Goals:**

- **不自動更新中選會選舉資料**。該資料每次選舉才變動一次，且 `data-spine-check.md` 記載其欄位順序會無預警改變、格式文件不更新——那需要人工判讀版面，不適合排程。
- **不自動更新原民會保留地資料**。年度更新，且來源為需人工點擊的 CSV。
- **不取用 SEGIS**。已於 `docs/segis-check.md` 評估後決定不取用。
- **不新增面板、不改動任何圖表的視覺呈現**。本次只動「數字從哪來」與「日期怎麼寫」。
- **不做 URL 狀態、不做等高線圖**。那是另外的改動。
- **不引入前端建置工具鏈**，維持無 npm 相依。

## Decisions

### 決策一：每日探測，以 ODRP 的回應語意判斷是否已發布

排程為每日一次（UTC 21:00，即臺北時間隔日 05:00）。

ODRP 對尚未發布的期別回傳 HTTP 200 並在 `responseMessage` 標示「查無資料」，不是 4xx。因此判斷依據是 `responseMessage` 與回傳列數，**不以 HTTP 狀態碼推測**。

探測範圍由 `data/sources.json` 目前記載的期別往後逐月推算至當月，取其中最新一個有資料的期別；若全部查無資料，視為尚無新期別。不寫死候選期別，也不假設「只會晚一期」——長期無人看管時可能一次落後多期。

**替代方案**：每週探測——最多延遲 6 天。對「首筆西拉雅族登記人數」這種有時效性的數字太久，而每日探測的成本只是一次 HTTP 請求。

### 決策二：以 workflow_dispatch 觸發既有的部署流程，不複製部署邏輯

以 `GITHUB_TOKEN` 推送的 commit **不會**觸發其他 workflow 的 `push` 事件（GitHub 的遞迴防護）。若不處理，資料會更新進版本庫但站台不會重新發佈。

處理方式是在提交成功後，以 `workflow_dispatch` 明確觸發既有的 `Deploy to GitHub Pages`。刷新流程因此需要 `contents: write` 與 `actions: write`，與 `deploy.yml` 目前的唯讀權限模型不同。

**替代方案**：把組建與發佈步驟複製進刷新流程——會產生第二條部署路徑，正是 `site-deployment` 的單一組建路徑要求所要避免的。

### 決策三：期別文字由組建時取代注入，這是 build-site.py 唯一被允許的轉換

`site/index.html` 內陳述基準日的位置改寫為佔位符，由 `scripts/build-site.py` 從 `data/sources.json` 讀取對應 `dataDate` 後取代。這是該腳本「只搬檔案」原則的唯一例外，並明確限制為單一種取代。

理由：這幾句話是「發佈時才知道正確值」的內容，讓它保持靜態就等於保證它會過期；而本機預覽與 CI 走同一支腳本，取代邏輯仍只有一處。

**替代方案一**：文案不再陳述具體期別（改寫成「基準日見下方資料來源」）——讀者失去判斷資料新舊的能力，對一個以時效為核心價值的專案是倒退。
**替代方案二**：全部交由 JS 在執行期渲染——停用 JavaScript 的讀者看不到基準日，牴觸 `dashboard-shell` 的可讀性要求。

### 決策四：平埔族群三態由資料判定，不由日期判定

平埔族群的呈現有三種狀態，判定依據一律是**載入的資料本身**，不是當前日期，也不是寫死的旗標：

- processed JSON 沒有 `indigenous_pingpu` 欄位 → 「該期官方統計尚無此欄位」，時間序列不補零。
- 有該欄位且值為 0 → 「欄位已存在，尚無人登記」。
- 有該欄位且值大於 0 → 顯示實際數字，並標註起算期別。

以日期判定會在 ODRP 延遲發布時說謊：登記已開放但該期資料還沒出來時，頁面會宣稱有登記數而實際載入的仍是零。

### 決策五：回歸測試以錄製的小樣本為輸入，並涵蓋失敗路徑

新增 `tests/run-regression.ps1`，以純 pwsh 斷言撰寫、失敗時以非零狀態碼結束，不引入測試框架。

輸入為 `tests/fixtures/` 下**人工構造但自洽**的小樣本，保留真實的欄位名稱與型別。不錄製完整回應：ODRP018 單期約 40MB，不宜入庫。

測試須同時涵蓋成功路徑與**既有自我驗證的失敗路徑**——另存刻意破壞的樣本（族別加總不等於 `indigenous_total`、平埔兩組結構混加造成重複計算），斷言腳本確實中止且不產出檔案。只測成功路徑等於沒測到安全網本身。

**替代方案**：Pester——額外相依，其輸出格式對本專案沒有加值；pytest——轉檔腳本是 pwsh，跨語言呼叫多一層沒有必要的複雜度。

### 決策六：變動幅度檢查，異常即中止

除了既有的加總自我驗證，新增一道幅度檢查：新期別的全國原住民總人口相對前一期的變動若超過 ±1%，視為異常並中止、不提交。

理由：加總自我驗證只能抓「內部不一致」，抓不到「內部一致但整份資料換了口徑」。實測近半年增幅為 1.30%（約每月 0.22%），±1% 的單月門檻有足夠餘裕，又能擋下數量級錯誤。

### 決策七：每期在 sources.json 新增一筆記錄，不就地覆蓋

刷新到新期別時，`data/sources.json` 新增該期的 ODRP013／ODRP018 記錄，既有期別的記錄原封保留。

理由：記錄裡有兩樣東西綁定特定期別——`notes` 寫著該期實際交叉驗證過的數字（11506 的全國
23,243,565 人、原住民 637,620 人與原民會月報相符），以及 `sha256`（該期原始檔的雜湊）。
就地覆蓋會讓 11506 驗證過的數字掛在 11507 的記錄上，那是憑空產生的假驗證。

自動新增的記錄 `verification` 記為 `unverified`、`notes` 註明「由排程刷新流程自動取得，
未經人工與原民會月報交叉驗證」。排程能做的是自我驗證與幅度檢查，做不到跨來源的人工核對，
記成 `primary-source` 是溢領。註冊檔每年因此多 24 筆，這個成本換得每期來源可各自追溯。

**替代方案**：就地更新同一筆——註冊檔不會長大，但過去各期的來源記錄只存在於 git log，
而 `sha256` 一旦被覆蓋，舊期別的原始檔就再也無法驗證。

### 決策八：processed JSON 不寫入產生時間

`Write-ProvenancedJson` 原本會蓋上 `_generatedAt = 今天`。移除該欄位，使轉檔成為純函數：
同一期別進去，同一串位元組出來。

理由：本次要求「重跑版本庫現有期別的產出須與既有檔案逐位元組相同」，而時間戳讓每次重跑
都產生假差異，把「資料變了」與「今天重跑過」混為一談——刷新流程正是要靠前者決定要不要提交。
該欄位沒有任何程式讀取，也沒有規格要求，而檔案何時產生由 git 歷史記錄且不可篡改。

**替代方案**：保留欄位但改由期別推導——那就與 `_sourceId` 重複，名字卻仍叫「產生時間」，
比沒有更容易誤讀。

## Implementation Contract

**行為：** ODRP 發布新期別後，最多一天內，站台上的人口數字、頁面上陳述的基準日、以及平埔族群的狀態文字三者同時更新到該期別。無新期別的日子，版本庫沒有任何新 commit、站台不重新發佈。

**介面與資料形狀：**

- 刷新流程接受手動觸發，並提供一個可指定期別的輸入，用於重跑特定期別。
- 期別探測的判定輸入是 ODRP 回應的 `responseMessage` 欄位與資料列數。
- 頁面基準日的來源鏈為：processed JSON 的 `_sourceId` → `data/sources.json` 對應項目的 `dataDate`。
- 組建腳本的取代對象是 `site/index.html` 中的期別佔位符，取代後的產物寫入 `_site/`，來源檔不被修改。
- 回歸測試以單一入口指令執行，成功時狀態碼 0，任一斷言失敗時為非零並在輸出指出失敗的斷言名稱。

**失敗模式：**

- ODRP 回應「查無資料」→ 正常結束，不提交，不視為失敗。
- 網路錯誤或非預期回應 → **流程失敗（紅燈）**。靜默失效比誤報危險：排程長期無人看管，紅燈是唯一會被注意到的訊號。
- 轉檔腳本的自我驗證失敗或幅度檢查未過 → 中止、不提交、流程失敗。
- 組建腳本找不到期別佔位符對應的來源記錄 → 組建失敗，不發佈。

**驗收條件：**

- 以指定期別手動觸發刷新流程重跑目前期別，確認產出與版本庫現有 processed JSON 逐位元組相同（冪等）。
- 暫時把 `data/sources.json` 記載的期別改為更早一期並觸發，確認流程取到較新期別、提交、且站台實際更新——不以流程顯示成功為唯一判準，須以瀏覽器開啟 Pages 網址確認頁面上的基準日已改變。
- 執行回歸測試入口指令：成功樣本狀態碼為 0；兩個破壞樣本皆為非零，且執行後沒有留下產出檔案。
- 停用 JavaScript 開啟站台，確認基準日仍出現在頁面上。
- 於本機以人工方式將 `indigenous_pingpu` 改為非零值後重跑組建，確認頁面由「尚無登記」切換為顯示數字，且時間序列的三態行為符合決策四。

**範圍邊界：**

- 在範圍內：ODRP013 與 ODRP018 的期別更新、基準日與平埔三態的資料驅動、轉檔回歸測試、刷新流程與部署流程的銜接。
- 在範圍外：中選會與原民會資料的更新、SEGIS、村里級資料、任何圖表視覺或版面的改動、URL 狀態、新面板。

## Risks / Trade-offs

- **[以 GITHUB_TOKEN 推送不會觸發 deploy.yml 的 push 事件，資料進版本庫但站台不更新]** → 決策二以 `workflow_dispatch` 明確觸發既有部署流程；驗收條件要求以瀏覽器確認站台實際更新，而非只看流程綠燈。
- **[人工構造的樣本無法偵測上游 schema 變動]** → 回歸測試守的是「我方解析邏輯不退化」，不是「上游沒變」。上游變動仍由腳本內建的自我驗證在執行期擋下並讓流程紅燈。這是刻意的分工，不是遺漏。
- **[自動提交可能把異常資料推上線]** → 既有加總驗證 + 決策六的幅度檢查 + 失敗即中止不提交，三層擋下。
- **[排程長期失效而無人察覺]** → 網路錯誤與非預期回應一律紅燈，GitHub 預設會通知版本庫擁有者；不採用「探測失敗當作沒有新資料」的靜默處理。
- **[±1% 幅度門檻可能誤擋真實的大幅變動]** → 西拉雅族登記開始後，平埔人口會從 0 跳到數萬，但那是 `indigenous_pingpu` 欄位的變動，總人口的變動幅度仍在門檻內。若日後出現合法的大幅變動，流程提供指定期別的手動觸發可在人工確認後放行。
- **[build-site.py 開了轉換的先例，日後可能被擴充成模板引擎]** → 決策三明確限定為單一種取代；規格層以要求的形式固定此邊界，而非僅靠註解。
